\title{\briskstate: A Cache-Aware State Backend for Apache Flink}

\author{Anonymous Authors}

\maketitle

\begin{abstract}
State access dominates the cost of many stream-processing pipelines once working sets outgrow cache capacity and garbage-collection overhead becomes visible at runtime. This paper presents \system, a cache-aware keyed state backend source design. The repository contains Java adapter interfaces, copy-on-write capture source paths, specialized primitive-key tables, and a native execution path for off-heap state management. Fresh native evidence passes 130 of 130 SwissTable, copy-on-write, serialization-round-trip, namespace, typed-state, and HotCache tests. In a tracked non-L0 Intel WordCount grid, \system outperforms the heap baseline in all 36 scanned configurations, with a 1.270$\times$ mean and 1.414$\times$ peak throughput ratio. These bounded results motivate controlled end-to-end and hardware evaluation.
\end{abstract}

\begin{IEEEkeywords}
stream processing, state backend, memory locality, CoW capture, Swiss tables
\end{IEEEkeywords}

\section{Introduction}

Stateful stream processing systems execute user logic over continuously evolving keyed state. In Apache Flink, this path is exercised by point updates, aggregations, joins, timers, windows, and checkpointing logic, so state management often dominates end-to-end performance once working sets exceed cache capacity or heap pressure increases \cite{carbone2015flink,carbone2017statemanagement}. Pointer indirection, object layout, probe locality, capture mechanics, state growth, and runtime memory management therefore motivate separate evaluation factors.

The default choices available to many Flink deployments present a familiar trade-off. Heap-resident state can deliver low software overhead while memory pressure remains moderate, but it becomes sensitive to object layout and garbage collection as state grows. Embedded persistent stores such as RocksDB bound heap growth and provide robustness, but they trade low-latency in-memory access for additional serialization, compaction, and storage-layer overhead \cite{rocksdb}. This leaves an open design space for more explicit state organization behind framework adapter surfaces.

This paper studies that design space through \system, a cache-aware keyed state backend that partitions state by key-group and namespace, stores entries in compact Swiss-table-inspired structures, and contains source paths for copy-on-write (CoW) views and batched asynchronous serialization. The implementation includes a Java class implementing Flink backend interfaces, specialized fast paths for primitive keys, and an optional native execution path for off-heap state management. These source-level interfaces are not themselves integration evidence.

The paper makes the following contributions.
\begin{itemize}
\item It presents the source-level design of \system around key-group partitioning, namespace-aware routing, compact Swiss-table-style storage, and CoW snapshotting.
\item It identifies the Java adapter, capture writer/reader, serialization proxy, and native-engine source paths; their presence is source evidence only.
\item It provides fresh native correctness evidence (130 of 130 tests) and a claim-to-artifact gate that separates native, framework-integration, software-only, and hardware evidence.
\item It reports the tracked non-L0 Intel WordCount grid as backend/layout evidence: all 36 cells favor \system, with a 1.270$\times$ mean and 1.414$\times$ peak throughput ratio over the heap baseline.
\end{itemize}

\section{Background and Motivation}

Modern stateful dataflow systems such as MillWheel, Naiad, Flink, Structured Streaming, and the Dataflow model define execution semantics for continuous queries, event time, and out-of-order processing, but they generally abstract away the physical state layout that ultimately determines runtime cost \cite{akidau2013millwheel,murray2013naiad,carbone2015flink,akidau2015dataflow,armbrust2018structured}. This abstraction is necessary for usability, but it can hide the source of performance instability when keyed state grows large enough that backend behavior becomes visible above operator logic.

Within Flink, keyed state is partitioned by key-group for scalability and checkpointing. This organization preserves determinism and enables redistribution, but each state access still depends on how keys, namespaces, and values are laid out inside the backend. Existing work on Flink state management and migration has focused on consistency, operational continuity, and reconfiguration cost rather than on exposing or optimizing memory-locality effects inside the backend itself \cite{carbone2017statemanagement,hoffman2019megaphone}. Meanwhile, recent storage and hash-table systems show that compact metadata, low-indirection probing, and careful update paths can change access cost materially \cite{chandramouli2018faster,abseil2018swisstable}.

The design motivates three evaluation questions; they are not retained artifact conclusions.
\begin{enumerate}
\item Whether memory budgets expose interactions among heap-resident state, GC, and object layout requires fresh matched evidence.
\item Whether compact key and metadata layouts change lookup, update, iteration, or removal cost requires fresh raw operator measurements.
\item Whether capture timing changes later writes, memory traffic, or execution variance remains a hypothesis for fresh measurement.
\end{enumerate}

These observations suggest that a keyed state backend should be designed as a systems component, not merely as a logical map hidden behind an API. The rest of the paper follows that perspective.

Two design principles guide the remainder of the implementation. \section{State Organization and Access Path}

This section describes how \system organizes keyed state and why the resulting access path differs from conventional heap-resident structures.

\subsection{Key-Group and Namespace Partitioning}

Flink routes keyed state through key-groups, which already provide a natural granularity for scalability, checkpointing, and reconfiguration. \system makes key-groups the first-class storage partition. For a state instance $S$, the logical mapping is:
\begin{equation}
S : \texttt{key-group} \rightarrow \texttt{namespace} \rightarrow \texttt{sub-table}.
\end{equation}

The source mapping aligns storage units with runtime reconfiguration units and routes each access to one sub-table. Whether this layout changes probe locality or cross-namespace interference remains an unverified hypothesis.

For void namespaces, the mapping simplifies to one sub-table per key-group. This fast path eliminates the namespace map entirely. For general namespaces, each key-group owns a namespace map whose values are sub-tables. Empty namespaces are removed eagerly after clears, which matters in window-heavy workloads where namespace churn is significant.

\subsection{Swiss-Table-Inspired Layout}

Each sub-table follows a compact layout inspired by Swiss tables. The design stores one control byte per slot in a contiguous control array and stores payloads in an interleaved array-of-structures (AoS) layout, where slot $i$ maps to the pair $(\texttt{entries}[2i], \texttt{entries}[2i+1])$ for key and value. The hash is split into a probe-dispatch component and a compact in-slot tag:
\begin{equation}
H_1 = \texttt{hash} \gg 7, \quad H_2 = \texttt{hash} \&\; 0x7F.
\end{equation}

The control byte stores either a special marker (empty or deleted) or the 7-bit $H_2$ fragment. During probing, \system loads groups of control bytes and compares them against a repeated pattern, enabling SWAR-style matching across several candidate slots at once. In the audited native implementation, a control group contains 16 bytes; architecture-specific and portable paths implement the matching operation.

This organization separates densely packed metadata from payload and stores each selected key beside its value in an AoS slot. Any change in cache-line traffic requires direct measurement and is not established here.

Figure~\ref{fig:layout} illustrates the resulting layout. The important point is not the exact byte encoding but the relative placement of routing metadata, control bytes, and payload arrays. The backend first narrows the search to one key-group and one namespace-specific sub-table, then probes compact control bytes, and only then touches the actual key/value payload.

\subsection{Specialized Primitive-Key Tables}

Generic object-key tables must rely on serializer output or object equality and incur boxing overhead when keys are primitive in logical form. \system therefore includes specialized tables for integer and long keys. These variants use primitive comparisons directly and can organize groups more compactly than generic object storage. A long-key group, for example, can be represented as one control word followed by a small block of keys, which reduces pointer chasing and shortens the distance between control metadata and payload.

This specialization is intended to shorten repeated update and lookup paths. Quantitative operator-level conclusions remain gated because the repository currently lacks the raw benchmark output needed to audit the derived comparison.

\subsection{State API Implementations}

The state-specific classes remain intentionally thin. ValueState maps directly to point read/update/remove operations over the state store. ListState and MapState add iteration and merge-like behaviors but still reuse the same key-group and namespace routing substrate. The keyed backend provides the current key and key-group index, so state classes can avoid redundant lookups or wrapper allocations on the hot path.

This is a design decision rather than a coding convenience. If routing, serializer interaction, and state-specific behavior are split across many layers, the state path becomes harder to reason about and optimize. \system therefore keeps state implementations close to the storage substrate and uses specialization only when it directly removes hot-path overhead.

\subsection{State-Specific Fast Paths}

The delivery design documents describe this principle more concretely as precomputed strategy selection for common key, namespace, and value combinations. The practical idea is simple: once a state descriptor is known, the backend can often choose a shorter path than a fully generic serializer-mediated route.

\section{Capture and Rehydration Source Paths}

The source tree contains capture, writer, reader, and rehydration entry points alongside the compact in-memory layout. Their presence describes source structure only; the audited boundary above applies.

\subsection{CoW Capture}

The synchronous source phase prepares immutable state views. Instead of serializing data immediately, the backend marks participating sub-tables and returns lightweight view objects that retain references to the current control and payload arrays. In effect, synchronous capture is reduced to metadata preparation and reference capture.

The source code captures table views and may lazily clone a table on its first later mutation. The resulting cost and memory effects are hypotheses that require fresh measurement.

\subsection{Asynchronous Serialization}

The asynchronous source path consumes captured views, accumulates serialized data in fixed-size chunks, and writes larger buffers to its output stream. Whether batching changes per-entry or kernel-write cost remains an unverified hypothesis.

The split between CoW capture and batched asynchronous serialization motivates two hypotheses for future measurement: a first mutation may incur a lazy clone, and a large captured view may lengthen asynchronous drain. The current evidence does not quantify either effect.

\section{Implementation Details}

\subsection{Backend Construction and Key Context}

The backend is organized around a keyed backend builder and a compact key context. The current key and current key-group index are made directly accessible to the state implementations so that repeated accesses can avoid unnecessary wrapper calls. This matters because the dominant operations in ValueState-heavy workloads are extremely short; if the surrounding framework adds even small layers of indirection, the storage optimizations become harder to observe in end-to-end behavior.

\subsection{Native Execution Path}

In addition to the Java source path, the repository includes a native state engine that stores state in off-heap Swiss tables and exposes operations through JNI. This path provides lower-level memory control and architecture-specific implementations. The native codebase includes its own test suite, storage specialization, and bug-fix history, including correctness fixes for control-byte cloning and empty-slot detection.

The native path is an implementation vehicle for off-heap state management and compact data-structure control. The retained Intel WordCount grid was collected without real L0 hardware, so it cannot establish an L0 effect or isolate which mechanism explains the measured result.

The production native table path uses \texttt{DefaultAllocator}, whose split-allocation extension returns one unified allocation. L0 memory is used only by the independent optional HotCache above StateTable. If the L0 device or runtime library is unavailable, HotCache is disabled while the native StateTable continues on the production allocator; this is a software-only boundary, not an equivalent L0 simulation. Incremental extendible-hash split is absent; split allocation is test-only, and production DefaultAllocator uses unified allocation.

At the C++ layer, the repository includes a native state engine whose Swiss-table implementation uses group-based matching and exposes state operations through a JNI bridge. Fresh native tests cover control-byte cloning, sentinel handling, and CoW-before-erase behavior. Higher-layer runtime semantics remain under the exact audited boundary above.

\subsection{Operational Characteristics}

Several implementation characteristics recur across the repository and evaluation artifacts.
\begin{itemize}
\item \textbf{Minimal routing on the hot path}: void namespaces skip one map lookup per state access.
\item \textbf{Compact metadata}: control bytes and payload arrays reduce pointer chasing.
\item \textbf{Specialization where it matters}: primitive-key tables remove boxing on common paths.
\item \textbf{Capture source path}: CoW capture and batched serialization are present without flattening the in-memory layout; no wire-protocol conclusion is drawn.
\end{itemize}

These choices are small individually, so the evaluation must isolate them rather than infer their effect from an end-to-end result.

\subsection{Interface and Deployment Constraints}

The repository's source and usage documents expose two deployment surfaces. First, an SPI service entry and versioned framework interfaces are present in the tree; this is source evidence only. Second, when the native engine is enabled, the TaskManager process must load the accompanying native library explicitly, so operational packaging remains part of the evaluation boundary.

These constraints shape the source and deployment inventory. Serializer and metadata proxies form part of the persistence surface. The native path also requires process startup, class loading, and container packaging to be evaluated together. Build, packaging, loading, and rehydration remain deployment evaluation items.

\subsection{Workloads}

We use three workload families.
\begin{itemize}
\item \textbf{WordCount grid sweep}: a ValueState-dominated microbenchmark that scans combinations of key cardinality and skew to isolate the repeated read-modify-write path.
\item \textbf{Operator-level state benchmark}: a JMH-style benchmark over representative ValueState, ListState, and MapState operations.
\item \textbf{NexMark}: end-to-end streaming queries with windows, ranking, joins, and other state-intensive patterns.
\end{itemize}

The workload set is intentionally layered: the state benchmark isolates operator cost, WordCount isolates repeated keyed-state access under controlled distributions, and NexMark embeds state access in realistic streaming pipelines. The latter two layers require fresh raw evidence before drawing comparative conclusions.

The benchmark harnesses also matter. The WordCount benchmark disables periodic persistence by default so that its retained measurement isolates steady-state state access. Capture-path interaction requires a separate fresh run with retained raw artifacts.

The evaluation plan includes throughput, query execution time, failure outcomes, and microarchitectural counters. Only metrics backed by indexed raw artifacts are retained as results in this revision.

The two documented platforms are not a controlled apples-to-apples comparison. This revision therefore withholds cross-platform behavior and causal conclusions.

\section{Discussion}

The present evidence supports a narrower discussion. The native suite verifies audited data-structure and native CoW cases; it also includes persistence round-trip cases. Separately, the retained non-L0 Intel WordCount grid records a comparative software-path result. The evidence does not establish operator-level, end-to-end query, profiler-derived, cross-platform, or real-L0 conclusions.

Whether a state backend changes physical access cost is an evaluation hypothesis; no broader causal conclusion is retained.

No single benchmark is sufficient to characterize a state backend. Operator-level tests can isolate point operations, WordCount can exercise repeated per-record state updates, and NexMark can combine windows, joins, checkpointing, and memory pressure. Only a matched matrix with raw artifacts can connect those layers or attribute an observed difference to state layout.

One hypothesis for backend builders is that probe structure, routing depth, serializer boundaries, and capture-time copying can become execution-path costs when jobs frequently access in-memory state. The current evidence does not establish their individual or end-to-end effects.

A future matched evaluation should vary state-access frequency and memory pressure to test when backend costs become measurable. No workload-dependent causal conclusion is retained in this revision.

The current implementation still leaves room for architecture-specific tuning and JNI batching. Their importance must be measured directly; the currently retained evidence cannot rank these sources of overhead.

Another limitation is that the current evaluation emphasizes read/update-heavy keyed state and selected NexMark queries rather than timers, large-window eviction patterns, and heavily write-amplified persistence schedules. Those cases remain future work.

\subsection{Broader Applicability}

WordCount and NexMark motivate future coverage of keyed aggregates, window state, and small per-key collections in SQL and Table pipelines. Broader applicability remains a hypothesis rather than a retained result.

The source tree contains binary-row conversion utilities, typed inner-map classes, and windowed namespace tests. Their presence is an implementation inventory, not evidence of higher-level workload applicability.

\section{Threats to Validity}

The documented Intel and Kunpeng environments are not a controlled cross-platform campaign. Cross-platform behavior and architectural attribution are therefore withheld pending fresh matched evidence.

The second threat is workload coverage. WordCount and the operator state benchmark target repeated keyed-state access, while NexMark covers broader streaming logic, but the operator and query layers lack fresh raw results in this revision. Timer-heavy workloads, very large namespace churn, and persistence-heavy deployment schedules also remain to be evaluated.

Finally, the implementation contains both Java and native paths, and the exact mix enabled in a production deployment can influence results. This is unavoidable for a backend designed to span on-heap and off-heap execution. The advantage of the present evaluation is that it exposes this fact directly rather than hiding it behind one synthetic path.

\section{Related Work}

\system lies at the intersection of stateful stream processing, storage-engine design, and runtime observability.

Stateful stream-processing systems such as MillWheel, Naiad, Flink, and Structured Streaming define the execution model for continuous queries and event-time processing, but they do not prescribe one physical state layout within the backend \cite{akidau2013millwheel,murray2013naiad,carbone2015flink,armbrust2018structured,akidau2015dataflow}. Work on Flink state management and migration has focused on fault tolerance, state redistribution, and correctness under reconfiguration rather than on the memory-locality properties of in-memory state structures \cite{carbone2017statemanagement,hoffman2019megaphone}.

At the storage layer, RocksDB remains an important point of comparison because it provides a mature persistent state backend with very different trade-offs in latency, serialization cost, and compaction behavior \cite{rocksdb}. \system explores a source design where keyed state remains memory resident and is laid out explicitly for compact access and CoW capture.

At the data-structure level, FASTER and Swiss-table-style indexing show that compact metadata and carefully structured probe paths can materially alter access cost in key-value workloads \cite{chandramouli2018faster,abseil2018swisstable}. \system borrows that insight in source classes that implement imported keyed-backend interfaces. This is a source adapter surface only; the exact audited framework boundary above applies. Benchmark suites such as NexMark provide end-to-end streaming workloads for a future fresh evaluation \cite{tucker2008nexmark}.

The nearest conceptual distinction between \system and prior stream-processing work is therefore one of emphasis. The stream-processing literature largely asks how to maintain consistent stateful execution in the presence of disorder, failures, and reconfiguration. \system asks a narrower source-design question: how should keyed state be laid out for a short and compact access path? Its runtime consequences remain hypotheses.

This difference in emphasis is worth underscoring. Systems such as Flink, MillWheel, and Structured Streaming established the semantics that make stateful stream processing practical. Namespace routing, metadata layout, persistence timing, and typed versus opaque map storage form concrete evaluation factors; \system contributes source mechanisms at that level of detail.

Compared with persistent stores such as RocksDB, the design space explored here is intentionally narrower and more memory-centric. The point is not to displace persistent LSM-based backends in all circumstances, but to study a source design that keeps keyed state close to the CPU and treats memory layout as a first-class concern. In that sense, the paper is closer in spirit to work on in-memory key-value stores and cache-conscious indexing than to work on durable storage engines. The source tree places these ideas beside imported keyed-state, namespace, and persistence interfaces; the exact audited framework boundary above applies.

There is also a useful distinction between \system and backend work that focuses primarily on migration or elasticity. Migration-oriented systems address when and how state moves between workers with low disruption. \system focuses instead on how state is represented and accessed while it remains local to one worker. Whether explicit key-group ownership affects migration is a future hypothesis, not a retained result.

Finally, the paper uses layout, locality, and data movement as evaluation hypotheses. Whether access-path changes, heap placement, or deferred serialization cause end-to-end differences requires fresh matched evidence.

\section{Conclusion}

This paper presented \system, a cache-aware keyed state backend source design. The tree contains key-group and namespace routing, compact Swiss-table-inspired layouts, specialized primitive-key paths, CoW capture code, and batched serialization code.

The fresh evidence verifies 130 native tests and retains a raw Intel WordCount grid with a 1.270$\times$ mean ratio and 1.414$\times$ peak. That grid is explicitly non-L0. The exact audited boundaries above remain in force. Operator-level raw output, end-to-end query logs, profiler exports, and real-L0 measurements remain required for broader conclusions.

The broader systems hypothesis is that physical state organization can matter once state access dominates execution. Broader framework-lifecycle and end-to-end conclusions are withheld under the audited evidence boundaries above.
